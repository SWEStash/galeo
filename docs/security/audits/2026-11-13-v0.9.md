| Low | 2 | **L1** `packaging/linux/rpm-after-install.tpl:31`, `packaging/linux/galeo.repo:2`, threat model T22 and RELEASING (*If the dnf subkey leaks*) all say that copying the key file to `/etc/pki/rpm-gpg/RPM-GPG-KEY-galeo` on each upgrade brings "rotations and revocations". That isn't how it works. rpm checks signatures against the certificate in **its database**, which dnf imports from `gpgkey=` only when a package fails with an unknown key. A newer file alone changes nothing. Measured in the pinned `fedora` image (rpm 6.1.0, dnf5 5.4.6), with a throwaway key (primary C, CI subkey A, standby S): with v1 (C+A+S) imported, a package signed by A **after** A was revoked in v2 still checks `digests signatures OK`. dnf5 installed it with `gpgkey=file://v2.asc` and `gpgcheck=1`, because nothing failed, so nothing was re-imported. A package signed by a new subkey B makes dnf5 import v2 (rpm 6 merges it into the stored certificate). Only after that does a package from A fail (`key is revoked`); `rpmkeys --import v2` does the same by hand. **Exploit**: the dnf subkey leaks; the owner follows RELEASING (revoke A, add B, ship a patch signed by standby S). Every Fedora machine upgrades without error, so v2 never reaches the rpm database, and A still signs packages and `repomd.xml` that those machines accept. That lasts until the first release signed by B, which may be never on machines that pin or stop upgrading. Delivery still needs a way to serve the package (Pages or a repository the user trusts), hence Low; the impact is root (T22). **Fix**: (a) in RELEASING's dnf leak steps, release notes tell Fedora users to run `sudo rpmkeys --import /etc/pki/rpm-gpg/RPM-GPG-KEY-galeo` once they have upgraded (rpm 6 then merges the revocation, as measured); (b) sign the release after the rotation with the new subkey soon, because its unknown key is what makes dnf import the file; (c) optionally add a second key source to `galeo.repo` before any user has it (I3), `gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-galeo https://swestash.github.io/galeo/rpm/galeo.asc`. Then the rotation release itself can be signed by B, and dnf fetches the revocation over HTTPS on the unknown key. Correct the two comments and T22 to say "rotations arrive with the first package signed by the new subkey; a revocation needs that import or `rpmkeys --import`". A `%post` can't run `rpmkeys --import` itself, because the transaction holds rpm's database lock. Text below. **L2** galeo's apt and dnf subkeys are subkeys of **one certificate** (`packaging/linux/galeo-archive-keyring.asc`). apt (`Signed-By` names the whole file) and rpm (which imports the whole certificate) accept a signature from **any** valid `[S]` subkey of it: in the L1 run, the standby subkey's package checked OK, as A's did. So the dnf subkey signs `InRelease` files apt accepts, and the apt subkey signs `.rpm` files rpm accepts. ADR-036 decision 4 and T22 ("a separate subkey from apt's, so one leak revokes one") are right about revocation but not about reach: either leak signs for both repositories. Before v0.9 a key apt trusts lived only in `github-pages`, which admits `main` only. Now it is also in `rpm-signing`, which admits `branch main` and **`tag v*`** (read with `gh api`). The only ruleset covers the default branch (no deletion, no force-push, linear history, required checks); **no ruleset covers tags**, and the environment has no required reviewer. **Exploit**: someone with write access, or a stolen token with `contents: write`, pushes a tag `v0.9.9` on any commit whose `release.yml` writes `$DNF_SIGNING_KEY` to its log or to a URL. The env policy admits the tag, `sign-rpm` gets the secret, and main's required checks never run. The workflow's own "tag is on main" check is in the file the attacker controls. The key then signs apt metadata and rpm packages for every galeo user. Today only the owner has write access, and write access can already reach `main` (T20 says so), so the tag adds a path that skips CI, not a new class of attacker: Low. **Fix**: a tag ruleset for `refs/tags/v*` (restrict creation, update and deletion; admin bypass only), and a required reviewer (the owner) on `rpm-signing`, so each release's signing waits for one click. Optionally a separate primary key for dnf, which needs a new ADR superseding ADR-036 decision 4. Correct ADR-036 decision 4 and T22 to say that either subkey signs for both repositories. |
