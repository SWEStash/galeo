## SR-10 Supply chain (apt bullet) — **PASS after L1**

- **Only a checked release is signed.** The assemble job, which holds no secret (`contents: read`,
  `attestations: read`), downloads the latest published release's `.deb` and `SHA256SUMS`, needs exactly one
  `.deb`, checks it with `sha256sum --strict`, and verifies its attestation: signed by `release.yml`, from that
  release's tag, on GitHub's runners. Any failure stops the run before the sign job, so the live site stays.
  `apt-repo.sh build` accepts only a `galeo` package for amd64, into a new folder.
- **The key is in one step.** `APT_SIGNING_KEY` is a secret of the `github-pages` environment, which only `main`
  deploys. Only the sign job names it, in one step's `env`; that step imports it into a keyring under
  `RUNNER_TEMP` and deletes the keyring on exit, before the apt check and the upload run. The job runs
  `actions/checkout`, `actions/download-artifact` and `actions/upload-pages-artifact` (pinned by SHA) and
  system tools; no npm package. `APT_SIGNING_PASSPHRASE` is empty except during a key rotation (RELEASING).
- **The result is proven.** `apt-repo.sh check` runs a rootless `apt-get update` and `apt-get download` trusting
  only the committed public key; any `E:`/`W:`/`Err:` line fails it. Its tests show it rejects a changed index,
  another key and no signature.
- **Key custody.** The primary key (certify only), the standby signing subkey and the revocation certificate are
  offline; the CI subkey alone was exported (`gh secret list` shows only `APT_SIGNING_KEY`). Fingerprints are in
  RELEASING.

## T20, T21 and the package's key

- The after-install script copies the packaged key (root-owned, under `/opt/galeo`) over
  `/usr/share/keyrings/galeo-archive-keyring.asc`, so a user's first, downloaded copy is replaced by the one
  `verify:package` checked against `packaging/linux/galeo-archive-keyring.asc`. The after-remove script deletes
  it on `remove` and `purge` only, so an upgrade never leaves apt without it.
- The first download trusts HTTPS to GitHub Pages; anyone able to change the site can already change the
  workflow (T20). The usage guide shows the fingerprint, and the `.deb`-first route starts from a checked file.
- No `Valid-Until` (T21, accepted): a stale `InRelease` can hold a user back, not install anything.

## Findings

### L1 — Low — a published release would deploy from its tag

`release: published` runs the workflow with `GITHUB_REF=refs/tags/v<version>`. The sign and deploy jobs use the
`github-pages` environment, whose only deployment rule is the `main` branch, so GitHub would refuse both and
the repository would never be published. Not a hole (it fails closed), but it defeats the feature. Fixed by a
`hand-over` job (`actions: write`) that runs `gh workflow run pages.yml --ref main`: a `workflow_dispatch` from
`GITHUB_TOKEN` is one of the events GitHub lets it start.

### I3 — Info — the signing job signs what the unprivileged job built

The jobs are split so the key never meets the code that handles the download. The sign job does not re-check
the `.deb` itself: whoever could change the assemble job's output could get it signed. Changing that output
needs the same write access to `main` that changing the workflow does, and the assemble job runs only GitHub's
pinned Actions and system tools on a checked file. Accepted; revisit if the assemble job ever runs npm code.
