## Summary

| Severity | Count | Items |
|---|---|---|
| Critical | 0 | — |
| High | 0 | — |
| Medium | 0 | — |
| Low | 1 | L1 `PdfExports.print` and `DiagramSaves.save` write with `fs.writeFileAtomic(path, bytes, { mode: 0o644 })` (`src/core/documents/pdf-export.ts:45`, `src/core/documents/diagram-save.ts:46`). That method `chmod`s the temp file to exactly 0644 and renames it over the target (`src/main/adapters/file-system.ts:222`). So, unlike a document save (`saveFile`, SR-15): the user's umask is ignored (umask 077 still gives a world-readable file); an existing file's mode and owner are dropped (a 0600 `report.pdf` becomes 0644); a symlink is replaced by a regular file instead of written through; a hard link is split; a file the user can't write is replaced as long as its folder is writable. Exploit: a reader with umask 077 exports a confidential document, or picks an existing private `report.pdf`, in a folder other local users can list (a shared project folder, `/tmp`); the PDF is now readable by every local account. No attacker is needed to trigger it, and the content is the reader's own, hence Low |
| Info | 5 | I1 neither `askPdfPath` nor `askSavePath` (`src/main/index.ts:993–1017`) passes `showOverwriteConfirmation`, which Electron documents as the Linux switch for "a confirmation dialog if the user types a file name that already exists". Whether the reader is asked depends on the dialog path (GTK or the desktop portal, which usually asks anyway); if not asked, typing the open document's own name (`notes.md` in a PDF export) replaces the source without a question. I2 `tabs.pin` (`src/main/tabs/handlers.ts:136`) needs no input, and `WarmTabs` exempts kept tabs from `count`, `bytes` and `pressure()` (`src/core/tabs/lifecycle.ts`): a compromised page can pin all its tabs, keeping each rendered and pinned across restarts (the session keeps `pinned`). It only reorders its own tabs and costs its own renderer memory, which such a page can spend anyway, so no new capability; but a reader who pins many large documents switches SR-14's warm budget and the memory-pressure path off for them. I3 Copy as rich text (`richTextOf`, `src/renderer/document/code-copy.ts`) puts the rendered article's HTML on the clipboard: the document's remote `<img src>` stays in it, so a mail client or rich editor that takes the paste may fetch an image galeo itself never loads (SR-04 holds inside galeo; the paste is the reader's act, as copying from a browser). Local images go as `galeo://file/<id>` (no path; they resolve nowhere else), `data-galeo-src` keeps the document's own relative path text. I4 `diagrams.save` writes the bytes the page sends: galeo's own SVG is DOMPurify output (`SVG_CONFIG` forbids `script`, `foreignObject`, `a`; only fragment URLs), but a compromised page could send an SVG with script to the file the reader names; the v0.7 threat model accepts this (the reader is creating that file). I5 `npm audit`: 6 moderate, all minimatch GHSA-g3hv-75wg-m249 under electron-builder 26.18.0, as in v0.6 |

## Attack surface delta (since v0.6.0)

| Entry point | Trust boundary | Controls verified |
|---|---|---|
| `diagrams.save(format, data, name)` | renderer → main; **writes a file outside edit mode** | zod union (svg: string 1..20 MiB; png: `Uint8Array` 1..20 MiB; name ≤ 200); main checks shape and byte size again, spends an input credit before the dialog; main's native save dialog, suggested name cleaned by `diagramFileName` (no folders, `.`/`..` words, control characters or leading dots, ≤ 80); writes only the picked path (`src/core/documents/diagram-save.ts`, `src/main/index.ts` `askSavePath`). Write mode: L1 |
| `documents.exportPdf(id)` → `documents.printPdf(token)` | renderer → main; writes a file | the id looked up in the sender's window, Settings refused (`assertDocument`), an input credit, main's dialog; a `randomUUID` token bound to the window, one use, 60 s, cleared on window close and on a new choice; the page never names a path (`src/core/documents/pdf-export.ts`). `printToPDF` without header or footer; the print copy is the same sanitized worker HTML through `mountDocumentHost`/`setTrustedHtml`, images only from the URLs main already granted the view, diagrams redrawn by the same sanitizing pipeline (`src/renderer/document/print.ts`). Write mode: L1 |
| `app.installProfileLauncher()` / `app.uninstallProfileLauncher()` | renderer → main; writes a desktop entry the session runs | no arguments (empty tuples); an input credit; the sender window's own profile only; Linux only, exec from `APPIMAGE` or the package's `galeo.desktop` `Exec`, absolute only; refused with a control character in exec or name; id must match `isProfileId` (`[a-z0-9-]`, ≤ 32); `Exec` quoted by the v0.5 `execArgument` (every Desktop Entry reserved character, `\\`, `%%`), files after `--` (SR-13); `Name`/`Comment` with `\` escaped; written only if absent or carrying `X-galeo-Profile=<id>`; removal likewise (`src/core/desktop/launcher.ts`, `src/main/app/handlers.ts`) |
| Profile delete | main | removes `galeo-profile-<id>.desktop` only while it carries that profile's mark; errors logged, never fatal (`src/main/index.ts`) |
| `tabs.menu(id)` | renderer → main; native menu | the tab looked up in the sender's window; main does Copy path and Reveal itself; the page gets back one of `TAB_MENU_CHOICES`; the tab is looked up again after the menu; a non-null choice earns one credit (`InputCredits.received`, 1 s, at most 5) |
| `documents.contextMenu(id, {tree, rich})` | renderer → main; native menu | strict object of two booleans (they only choose which items show); `assertDocument`; Open with default app re-checked after the choice (SR-05, unchanged); the result dropped if the tab closed or changed file meanwhile; **Edit** runs main's own `toggleEditMode` and only when the menu's tab is the window's shown tab (ADR-013/015 question and grant as for Ctrl+E); other choices come back as `DOCUMENT_MENU_CHOICES`; a choice earns one credit, so Save spends it as Ctrl+S |
| `tabs.pin(id, pinned)` | renderer → main | `documentId`, boolean; the sender's own tab, never Settings; reorders only (I2) |
| Session file | disk → main | version 2 adds `pinned: z.literal(true).optional()` on a `strictObject`; 1 → 2 migration is the identity; the 4 MiB cap (SR-17) and restore clamping (`within`) keep the pinned block consistent even for a hand-edited file |
| Code Copy buttons, Copy as rich text | renderer → clipboard | `clipboard-sanitized-write` was already the one permission allowed (SR-01, `src/main/window/policy.ts:4`); buttons built with `createElement` and constant strings, the copied code is `textContent`; rich text is a clone of the already-sanitized article without galeo's own controls (I3) |
| Test hooks | env → main | `GALEO_TEST_SAVE_PATH` read only under `!app.isPackaged` (both dialogs); `GALEO_TEST_PROFILE_LAUNCHER_EXEC` only in the `!packaged` branch of `profileLauncherExec`, absolute only; e2e launches set `XDG_DATA_HOME` to the test home, so no test writes the real applications folder (`tests/helpers/launch.ts`) |

Nothing changed in the preload's shape beyond the new channels, window creation, CSP, fuses or the permission
handler: SR-01, SR-02, SR-06 and SR-08 carry over (the title-bar overlay colour and height are cosmetic). All seven new

## Per-SR verification (SRs the delta touches)

- **SR-02/SR-03 content is inert — PASS.** The print copy and rich-text copy reuse the sanitized worker HTML; no new
  HTML sink in `src/` (the new `innerHTML` uses are in tests, and `richTextOf` reads `innerHTML` of a clone); icons
  are galeo's own SVG elements.
- **SR-04 no network — PASS with I3.** Printing loads only granted `galeo://file/` images under the same CSP.
- **SR-05 opening files — PASS.** Unchanged: the menu re-checks before Open with default app.
- **SR-09 engine updates — PASS.** Electron 45.2.3 is the latest 45.x and `latest` on npm (checked 2026-11-06).
- **SR-10 supply chain — PASS with I5.** New in the delta: `shiki`/`@shikijs/rehype` 4.6.0 and `@vitejs/plugin-react`
  6.2.1, both minor bumps of listed dependencies; no new package.
- **SR-11 minimal, validated IPC — PASS.** Seven channels, each zod-validated, scoped to the sender's window.
- **SR-12 capability-scoped file access — PASS.** Both new writes go only to a path main's own dialog returned after
  real input; the page never names a path. The menu credit is a native-menu click, equivalent to the key press it
  stands for (T6 unchanged); a dismissed menu earns nothing.
- **SR-13 command lines — PASS.** The profile launcher passes files after `--` and quotes its Exec as v0.5 does.
- **SR-14 bounded work — PASS with I2.** Diagram data ≤ 20 MiB, PNG canvas ≤ 16 384 px a side, print waits ≤ 10 s
  for diagrams.
- **SR-15 safe saves — FAIL before the L1 fix, PASS after it.** Document saves are unchanged, but the two new writes don't follow SR-15's
  rules on mode, ownership, symlinks and write protection.
- **SR-17 local metadata files — PASS.** Session v2 is a strict, bounded addition.

## Open questions

Answered by the owner on 2026-11-06: L1 as document saves, I2 a last resort under memory pressure, I3
accepted (see *Status after fixes*). I1 stays for the manual check.

1. **I1**: does Electron 45's save dialog on Ubuntu 26.04 (GNOME, Wayland: the portal) ask before overwriting? A
   manual check with an existing `x.pdf`; the property is harmless either way.
2. **L1 scope**: should an export onto an existing file keep that file's mode and owner (SR-15 as for saves, the
   recommended fix), or is "a new file each time, umask applied" enough? Either way the forced 0644 should go, and the
   threat model's "with the usual file permissions (0644)" changes with it.
3. **I2**: is "a pinned tab is never hibernated, even under memory pressure" the intended rule (then SR-14 should say
   so), or should pressure still take the least recently shown pinned tab last?
4. **I3**: accept as the reader's act, or strip remote `src` from the rich-text copy? Stripping would break pasting
   documents whose images are on the web, which is the usual reason to copy as rich text.
